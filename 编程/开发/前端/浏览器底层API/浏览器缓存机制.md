## 缓存机制概述

浏览器缓存是提升 Web 性能的核心手段之一。通过将经常访问的静态资源（如 HTML、CSS、JavaScript、图片）存储在本地，可以显著减少网络延迟、降低服务器负载，并实现更快的页面加载。浏览器的 HTTP 缓存策略主要分为两类：强缓存与协商缓存。

## 强缓存

当强缓存命中时，浏览器直接从本地缓存（Memory Cache 或 Disk Cache）中读取资源，**完全不会向服务器发送任何网络请求**。返回的 HTTP 状态码通常为 200（并在 Network 面板中标记为 `from memory cache` 或 `from disk cache`）。

### 核心 HTTP 响应头

1. **`Expires` (HTTP/1.0)**：
   - 值为一个绝对的 GMT 时间字符串，表示该资源的过期时间。
   - **缺点**：受限于客户端本地时间，如果客户端修改了本地时间，会导致缓存失效判断错误。
2. **`Cache-Control` (HTTP/1.1)**：
   - 现代浏览器主要依赖的缓存控制字段，优先级高于 `Expires`。
   - 常用指令：
     - `max-age=<seconds>`：设定资源被缓存的有效时长（相对时间，如 `max-age=31536000`）。
     - `no-cache`：绕过强缓存，**必须向服务器发起协商缓存验证**。
     - `no-store`：绝对禁止任何缓存，每次都向服务器请求完整的新资源。
     - `public`：允许浏览器和代理服务器（CDN）缓存。
     - `private`：仅允许最终用户的浏览器缓存。

## 协商缓存

当强缓存未命中（例如 `Cache-Control: no-cache` 或时间已过期）时，浏览器会向服务器发起请求，并带上上一次请求获取的资源标识。服务器通过对比这些标识，判断资源是否发生过修改。
- **未修改**：服务器返回状态码 `304 Not Modified`，不返回资源实体，告知浏览器继续使用本地缓存。
- **已修改**：服务器返回状态码 `200 OK`，并附带最新的资源内容及新的缓存标识。

### 核心 HTTP 头部组合

协商缓存依赖两组请求头与响应头的配合：

1. **`Last-Modified` / `If-Modified-Since` (HTTP/1.0)**：
   - **机制**：服务器在响应头中通过 `Last-Modified` 返回资源的最后修改时间。浏览器下次请求时，在请求头带上 `If-Modified-Since`，值为上次的修改时间。服务器对比本地文件的最新修改时间与该值。
   - **缺点**：时间精度仅精确到秒；有时文件修改时间变了但内容未变，也会导致重新传输。
2. **`ETag` / `If-None-Match` (HTTP/1.1)**：
   - **机制**：服务器在响应头中通过 `ETag` 返回基于资源内容生成的唯一标识（如哈希值）。浏览器下次请求时，在请求头带上 `If-None-Match`，值为上次的 ETag。服务器比对文件的当前 ETag。
   - **优势**：精度极高，只要文件内容未变，即使修改时间改变也能命中缓存。`ETag` 的优先级高于 `Last-Modified`。

## 缓存位置

浏览器缓存按存储位置分为以下几类（查找优先级从上到下）：
1. **Service Worker**：由开发者自由控制的缓存层，优先级最高。
2. **Memory Cache**：内存中的缓存，读取速度最快，但生命周期极短（随标签页关闭而清空），通常用于缓存网页中的图片或脚本等小文件。
3. **Disk Cache**：硬盘中的缓存，读取速度较慢，但容量大且持久保存，适用于大文件及长效缓存资源。
4. **Push Cache**：HTTP/2 中的服务器推送缓存。
