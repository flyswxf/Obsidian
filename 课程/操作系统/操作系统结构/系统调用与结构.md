## 操作模式

为了确保操作系统正常运行并保护系统资源免受错误或恶意程序的破坏，硬件层面通常提供至少两种独立的操作模式：**用户态**（User Mode）和**内核态**（Kernel Mode）（也称为管态、系统态或特权态）。
### **用户态**：
当计算机系统代表用户应用程序执行时，系统处于用户态。在此模式下，程序只能访问有限的资源，不能执行特权指令（如直接访问硬件设备、修改内存管理寄存器等）。
### **内核态**：
当用户应用程序请求操作系统服务，或者系统响应中断与异常时，系统会切换到内核态。在此模式下，操作系统拥有对所有硬件和内存的完全访问权限，可以执行任何 CPU 指令。
### 模式切换机制

硬件中通常设有一个**模式位**（Mode Bit）来指示当前的运行模式（例如，内核态为 $0$，用户态为 $1$）。
当用户程序需要执行特权操作时，必须通过触发**陷入**（Trap）或软件中断，向操作系统发出请求。此时，硬件会将模式位从 $1$ 切换为 $0$，并将控制权交接给操作系统内核。内核完成请求的服务后，在将控制权交还给用户程序之前，会将模式位重新恢复为 $1$。这种通过软件中断请求系统服务的机制，正是实现[[系统调用与结构#系统调用基础|系统调用]]的核心基础。

## 系统调用基础

系统调用提供了操作系统所提供服务的编程接口。这些调用通常以 C 或 C++ 语言编写的例程形式提供，对于某些底层任务，可能需要使用汇编语言。应用程序通过这些接口向操作系统内核请求执行特权操作。

虽然可以通过软件中断（如陷入 Trap）直接触发系统调用，但应用程序开发者通常依赖于应用程序编程接口（API）。常见的 API 包括适用于 POSIX 系统的 POSIX API、适用于 Windows 系统的 Win32 API 以及适用于 Java 虚拟机的 Java API。使用 API 的优势在于程序的代码可移植性以及它封装了底层系统调用的复杂细节。应用程序正是通过这种方式来获取[[操作系统服务与接口#操作系统服务|操作系统服务]]的。

### 参数传递机制
在发起系统调用时，经常需要向操作系统传递参数。常见的参数传递方法包括：
1. **寄存器传递**：最简单的方法是将参数存入寄存器中。然而，在某些情况下，参数的数量可能超过了可用的寄存器数量。
2. **内存块/表传递**：当参数较多时，可以将参数存储在内存的块或表中，并将该块的内存地址作为一个参数存入寄存器传递给操作系统。Linux 和 Solaris 均采用这种方法。
3. **堆栈压入与弹出**：参数也可以由程序压入（Push）堆栈中，并由操作系统从堆栈中弹出（Pop）。
块传递和堆栈传递都不限制传递参数的数量或长度。

## 操作系统结构

随着操作系统变得越来越庞大和复杂，它们必须经过精心设计才能正常运行并易于修改。

### 简单结构（单体结构）
最初的操作系统（如 MS-DOS 和早期的 UNIX）并没有良好的结构。它们只是由许多过程组成，任何过程都可以随意调用其他任何过程。整个操作系统作为一个单一的可执行文件在内核态运行。这种结构的优势在于由于系统调用开销小，运行效率高；缺点是难以维护，一个部分的错误可能导致整个系统崩溃。

### 分层方法
为了改善单体结构的缺点，分层方法将操作系统划分为若干层（级别）。最底层（第 0 层）是硬件，最高层（第 N 层）是用户界面。每一层都建立在较低层的基础上，并且只使用较低层提供的功能和服务。这种结构简化了调试和系统验证。

### 微内核结构
微内核结构（Microkernel）通过将所有非必要组件从内核中移除，并将它们作为系统级或用户级程序来实现，从而对操作系统进行模块化。微内核通常只提供最小的进程和内存管理，以及通信功能。
客户端程序和运行在用户空间的各种服务之间通过消息传递进行通信。这种通信严重依赖于[[进程间通信_IPC#IPC 的两种基本模型|进程间通信]]机制。微内核的主要优点是易于扩展操作系统、便于移植到新的硬件架构，以及提供了更好的安全性和可靠性。

### 模块化结构
现代操作系统的最佳方法是使用可加载的内核模块（Loadable Kernel Modules, LKM）。内核提供核心服务，而其他服务则在内核运行时动态实现。这结合了分层系统的模块化和单体系统的高效性，因为模块直接加载到内核空间中运行，不需要像微内核那样进行昂贵的消息传递。
