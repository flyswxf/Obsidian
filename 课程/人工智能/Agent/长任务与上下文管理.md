长任务的核心矛盾是：任务执行过程不断产生信息，但模型每次推理能够直接看到的信息是有限的。代码、命令输出、错误日志、用户约束、已完成决策和待办事项都会竞争同一个上下文窗口。有效的长任务管理，不是让模型“记住一切”，而是持续维护一份足够精确、可恢复、可检索的任务状态。

## 先区分两个“记忆”

**模型上下文**是当前请求发送给模型的输入内容，通常包括系统指令、用户消息、历史对话、工具调用及工具返回结果。它是模型本轮推理可以直接访问的工作区，但容量有限，并且会随着对话持续增长。

**外部持久化**是上下文之外保存的信息，例如文件、数据库、向量库、任务队列、版本控制记录或工具服务中的状态。它不会自动进入模型的注意范围，必须通过读取、查询或工具调用重新取回。

两者的边界可以概括为：

$$
\text{本轮可用信息}=\text{当前上下文}+\text{本轮检索或工具返回的信息}
$$

写入文件不等于模型已经“记住”；只有后续把文件内容读回上下文，持久化状态才重新参与推理。反过来，当前上下文中的临时判断若没有写入外部介质，会随着会话截断、压缩或结束而丢失。

## Context window 是什么

Context window（上下文窗口）是模型一次处理的 token 总预算。token 不完全等于字符或单词，中文文本、代码、路径和格式符号的切分方式不同。窗口通常同时容纳：

- 系统指令、工具定义和安全约束；
- 用户的任务描述与历史对话；
- 模型之前的回答；
- 工具调用参数、命令输出、文件内容和错误日志；
- 当前正在生成的回答。

因此，标称窗口大小不能全部视为“可写入的历史空间”。工具定义很长、日志很大或输出即将生成时，可用于旧对话的预算会进一步减少。

上下文窗口是**每次推理的输入边界**，不是一个跨会话的硬盘，也不是模型参数本身。模型参数保存的是训练得到的模式，不能可靠地保存某个任务刚刚产生的文件状态、用户偏好或未提交的决策。

可以把单次推理抽象为：

$$
y_t=\operatorname{Model}(I,S_{0:t},T_{0:t-1},M_t)
$$

其中 $I$ 是系统指令，$S_{0:t}$ 是到当前时刻的对话片段，$T$ 是工具交互，$M_t$ 是本轮主动取回的外部记忆。模型只依据被放入输入的内容生成 $y_t$。

## 11 小时或数天任务是否应该单会话

“单会话”与“单次连续上下文”不是同一件事。一个任务可以有稳定的会话标识，但在内部经过多次摘要、上下文重建或重新加载；也可以真的把数天所有消息都保留在一个不断增长的历史中。

对 11 小时或数天任务，默认不应依赖未经管理的单一长会话。原因包括：

1. 历史消息会挤占新任务需要的空间；
2. 早期约束在压缩时容易被遗漏或改写；
3. 大量代码和日志降低检索相关信息的比例；
4. 工具状态、工作区文件和模型所描述的状态可能发生分叉；
5. 服务重启、超时、模型切换或权限变化会使连续性中断。

更稳妥的形态是“短上下文循环 + 外部任务状态”。每个阶段使用一个可控大小的上下文，阶段结束时写入检查点；下个阶段从检查点、当前文件和少量相关证据恢复。若任务仍处于同一逻辑阶段，保持同一会话有利于保留局部语境；跨阶段则应主动重建上下文，而不是无限追加历史。

适合单会话连续推进的情况是：任务短、状态主要在对话中、工具输出很少，且失败后重新执行成本低。适合分段恢复的情况是：涉及大量代码、长时间运行、多人协作、外部服务、不可逆操作或需要审计。

## 摘要与压缩

**摘要**是把一段历史转换为更短的语义表示；**压缩**是更广义的上下文缩减，包括删除重复信息、折叠工具输出、截取日志、保留文件差异以及生成结构化状态。压缩不是简单截断，质量取决于哪些信息被保留。

摘要至少应保留四类内容：

- 目标：任务要达到的可验证结果；
- 约束：不可违反的规则、接口、目录、格式和验收标准；
- 状态：已经完成什么，当前文件或服务处于什么状态；
- 决策：采用了哪些方案，为什么，哪些方案已被排除。

只保留“已经做了很多工作”会造成伪连续性，因为下一个阶段不知道如何验证，也不知道哪些假设仍然成立。适合恢复的摘要应使用结构化格式，例如：

```text
任务目标：
硬约束：
已完成：
当前状态：
关键决策：
已知问题：
下一步：
验证命令：
相关文件：
```

压缩时应优先保留约束和可验证状态，其次保留决策与未解决问题，最后才保留冗长的过程性对话。完整代码不应反复塞进摘要；代码以工作区文件或版本记录为准，摘要只记录文件路径、关键接口、变更意图和验证结果。

## 滑动窗口

滑动窗口只保留最近一段消息，或保留“固定摘要 + 最近消息”的组合：

$$
C_t=S_{\text{summary}} \oplus S_{t-k:t}\oplus M_t
$$

其中 $S_{\text{summary}}$ 是历史摘要，$S_{t-k:t}$ 是最近 $k$ 个交互，$M_t$ 是本轮检索内容。它能控制上下文增长，但存在“最近不等于重要”的问题。早期的用户约束、接口契约或失败原因可能比最近一条日志更重要。

因此滑动窗口不能单独使用。应把长期有效的信息提升到稳定摘要或外部状态文件，把短期细节留在最近窗口，把具体事实放在可检索的源文件中。窗口大小还应为工具定义、当前任务说明和模型输出预留预算。

## 外部记忆与分层记忆

外部记忆的价值不在于保存越多越好，而在于保存“下次恢复时真正需要的事实”。可以采用分层结构：

| 层级 | 内容 | 典型载体 | 访问方式 |
| --- | --- | --- | --- |
| L0 当前工作集 | 当前问题、最近工具结果、正在编辑的片段 | 当前上下文 | 直接注意 |
| L1 阶段状态 | 目标、约束、进度、阻塞和下一步 | `checkpoint.md`、任务 JSON | 每轮读取 |
| L2 项目事实 | 文件结构、接口、设计决策、测试命令 | 项目文档、提交记录 | 按需读取 |
| L3 历史资料 | 旧方案、长日志、原始对话、实验数据 | 文档库、对象存储 | 检索后读取 |

L0 追求反应速度，L1 追求可恢复，L2 追求一致性，L3 追求完整留档。不同层级不应混成一份无限增长的“万能记忆”。

外部记忆可以是结构化数据库，也可以是普通 Markdown 文件。结构化数据适合状态机、任务依赖和精确更新；Markdown 适合人类审阅和保留解释。向量检索适合从大量语义相近的资料中召回候选，但不能替代精确的文件读取、版本号和状态字段。涉及代码时，优先通过路径、符号、提交记录或测试结果定位事实，再使用语义检索补充背景。

## 检索：把信息取回，而不是把所有信息带上

检索增强的基本流程是：

1. 将当前目标转换为查询，例如文件名、函数名、错误信息、接口或概念；
2. 从索引、文件树、数据库或版本记录中召回候选；
3. 依据路径、时间、版本、权限和任务相关性过滤；
4. 只把必要的原文片段送入当前上下文；
5. 在操作后写回新的状态与证据。

检索结果必须带来源，否则模型容易把相似片段误认为当前事实。代码检索尤其需要同时关注定义、调用方、测试和最近变更。仅召回函数定义，可能遗漏调用约定；仅召回错误日志，可能遗漏已经修复的状态。

可将取回策略写成一个简单目标：

$$
\max_{R}\ \operatorname{relevance}(R)-\lambda\operatorname{tokens}(R)
$$

其中 $R$ 是送入上下文的证据集合，$\lambda$ 表示 token 成本。高质量检索不是返回最多内容，而是在有限预算内返回足以支撑当前决策的证据。

## 工具状态与模型状态

工具状态是文件是否已写入、进程是否运行、数据库是否提交、远程任务是否完成、当前分支和依赖版本是什么。模型状态是模型对这些事实的描述。两者可能不一致：

- 模型以为文件已经修改，但工具调用失败；
- 命令返回了旧缓存，模型误判为最新结果；
- 长任务期间进程退出，但上下文仍描述“正在运行”；
- 外部人员修改文件，旧摘要继续指导操作。

任何有副作用的动作都应以工具返回结果或再次读取为准。状态记录应包含时间、版本或运行标识，必要时记录校验和。对长时间任务，最好把“计划状态”和“事实状态”分开：计划写入任务清单，事实通过文件读取、测试、查询或服务健康检查确认。

## 检查点与恢复

检查点是可独立解释的恢复单元，不只是“阶段完成”的一句话。一个合格检查点至少记录：

```text
checkpoint_id:
更新时间：
任务目标：
当前阶段：
已确认事实：
已修改文件：
验证结果：
未解决问题：
下一步动作：
恢复所需工具和环境：
```

写检查点的时机包括：完成一个可验证阶段后、进行不可逆操作前、发现新失败模式后、上下文即将压缩前以及会话结束前。检查点应尽量原子化，先写临时文件并完成校验，再替换正式文件，避免进程中断留下半份状态。

恢复时不要只读取摘要，还应验证摘要中的关键事实：检查当前分支和文件差异，读取目标文件，确认进程或服务状态，再执行下一步。恢复流程可以概括为“读取检查点 → 验证环境 → 读取最小相关证据 → 更新计划 → 执行一个可验收动作”。

## 当前常见做法的缺陷

**把整段聊天当数据库。** 历史消息既不容易精确查询，也不保证永久存在。解决方法是把目标、约束、决策和状态显式写入外部文件。

**把所有代码和日志原样塞回上下文。** 这会消耗 token，并让关键错误埋在噪声中。解决方法是保存原始日志，当前上下文只取相关时间段、错误栈和验证结论。

**只做自然语言摘要。** 摘要可能省略否定条件、路径、版本和未完成事项。解决方法是采用固定字段，并保留可验证证据。

**只依赖向量检索。** 语义相似不代表版本正确，也不能保证包含精确符号。解决方法是将关键词、路径、结构化查询和语义检索组合使用。

**认为工具调用成功就代表任务成功。** 工具成功只表示命令被接受或执行完成，不一定表示业务目标达成。必须追加测试、读取、查询或人工验收。

**无限重试失败动作。** 没有记录失败原因时，重试会重复同一错误并污染上下文。每次失败应记录输入、输出、假设和下一种尝试；达到阈值后暂停并重新评估方案。

**把压缩后的摘要当成事实。** 摘要是派生信息，可能过期。源文件、测试结果、提交记录和服务查询才是事实依据。恢复时应优先验证外部状态。

## 一套可执行的长任务流程

开始时先建立任务状态，明确目标、验收标准、限制条件和初始检查点；执行时只把当前阶段所需信息放入上下文，每完成一个小阶段就更新状态；上下文接近预算上限时，生成结构化摘要并清理重复历史；跨会话时读取检查点并验证工作区；结束时保存最终结果、验证证据、遗留风险和后续入口。

对于代码型 [[Agent]] 任务，工作区文件、测试命令和版本记录应作为事实源；对话只承担决策与协调。对于需要大量资料的任务，[[检索增强生成（RAG）]] 负责召回证据，摘要负责维护阶段状态，检查点负责跨会话恢复，工具负责确认真实环境。若任务涉及多个阶段，可用 [[工作流编排]] 或状态机表达依赖，使“下一步”不依赖模型临时回忆。

最终可用一句话判断设计是否可靠：即使当前会话立即中断，换一个干净上下文，凭借外部状态和验证命令，是否能在较短时间内恢复到正确位置。若不能，缺少的通常不是更大的上下文窗口，而是更清晰的状态、证据和检查点。
