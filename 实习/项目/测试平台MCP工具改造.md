## 背景

团队使用某测试平台管理测试用例，日常工作中需要将自动化连跑的测试结果标注到平台。原有方案是通过一个 MCP Server 提供 **40+ 个工具**，涵盖认证、用例搜索、用例导入导出、任务创建执行、特性查询、APITest 调试等。

但实际上，日常 90% 的场景只需要其中一个组合工具——"设置用例结果（完整流程）"。

**问题**：40+ 个工具的 schema（参数名、类型、描述）全部注入模型上下文，占用约数万 token，但实际只使用其中 1 个。这导致：
- 模型上下文被大量无用 schema 占据，影响推理质量
- 工具名称极长（如 `mcp__xxx_xxx_server__set_test_case_result_complete`），调用时消耗大量 token
- 中间结果（cookie、token、用例详情等）全部回传到模型上下文，既浪费又存在数据暴露风险

## 改造思路

参考 Anthropic 博客[Code execution with MCP: building more efficient AI agents \ Anthropic](https://www.anthropic.com/engineering/code-execution-with-mcp)中的核心理念：

> **让数据在工具之间流动，但不经过模型。中间结果留在执行环境，只有 `print()` 的内容才进入模型上下文。**

这篇文章提出了一个关键洞察：MCP 工具调用的返回值默认会进入模型上下文，但对于很多场景，模型不需要看到中间数据——它只需要知道"操作成功了"还是"操作失败了"。

以我的场景为例，标注一个用例需要 5 步 API 调用：

```
搜索用例 → 保存执行记录 → 设置测试结果 → 确认结果 → 设置测试记录
```

每一步的返回值（用例 URI、workspace_id、执行记录等）对模型来说都是无意义的中间数据。模型只需要知道最终结果：成功还是失败，标注到了哪个用例。

博客的核心启示是：**不是所有工具交互都需要通过 MCP 工具注册**。当 Agent 只使用少量工具时，代码执行模式更优——Agent 直接写代码调用一个轻量模块，中间结果留在执行环境，模型只看到 `print()` 的摘要。

## 改造实践

### 原有架构

原 MCP Server 注册了 40+ 个 `@mcp.tool()` 工具：

```
mcp_server/
├── main.py              # 入口
├── logic.py             # 2800+ 行，注册 40+ 个工具
└── tools/
    ├── auth.py          # 认证
    ├── config.py        # 配置读取
    ├── testcase_search.py    # 用例搜索
    ├── testcase_result.py    # 用例结果设置（5步组合）
    ├── testcase_detail.py    # 用例详情
    ├── testcase_import.py    # 用例导入
    ├── task_create.py        # 任务创建
    ├── task_execution.py     # 任务执行
    └── ... (20+ 其他模块)
```

每个工具都有完整的参数 schema（参数名、类型、描述、示例），这些 schema 在 MCP 协议握手时全部注入模型上下文。但我实际只使用其中一个组合工具，其余 39 个工具的 schema 纯粹是上下文噪音。

### 改造后架构

将 mcp 工具中实际使用的逻辑提取为一个约 500 行的 Python 脚本

Agent 的调用方式从 MCP 工具调用简化为一行命令：

```bash
python upload_test_result.py
```

脚本只输出一行摘要：`✅ 用例结果设置成功 | 用例: TC_XXX | 结果: 通过`

中间的 5 步 API 调用、cookie/token、用例详情等数据全部留在进程内，模型完全不需要看到。

## 成果对比

| 维度      | 改造前（MCP 方式）                                    | 改造后（代码执行方式）                    |
| ------- | ---------------------------------------------- | ------------------------------ |
| 模型上下文占用 | 40+ 工具 schema ≈ 数万 token                       | 0（无 MCP 工具注册）                  |
| 实际使用工具数 | 1 / 40+（2.5%）                                  | 不适用（直接代码调用）                    |
| 调用方式    | `mcp__xxx__set_test_case_result_complete(...)` | `python upload_test_result.py` |
| 中间数据    | cookie、token、用例详情等全部进入上下文                      | 只有 `print()` 摘要进入上下文           |
| 代码量     | 2800+ 行主逻辑 + 20+ 工具模块                          | 约 500 行单文件                     |

## 关键收获

1. **MCP 适合工具多且动态选择的场景**：当 Agent 需要根据情况从几十个工具中选择时，MCP 的工具发现机制有价值。但当只固定使用 1 个工具时，40+ 个工具的 schema 纯粹是上下文噪音。

2. **代码执行是 MCP 的自然补充**：Anthropic 博客的核心启示是——不是所有工具交互都需要通过 MCP 协议。代码执行模式让中间数据留在执行环境，只有 `print()` 的内容进入模型上下文，既节省 token 又保护数据。
